## Manifest repair

[The upstream manifest](../manifest/cm-10.2.0-upstream.xml) used a moving stable branch for most CM projects even at the release tag. The recovered manifest pins surviving release tags first, then resolves remaining stable references. It preserves AOSP Android 4.3.1 pins, checks the CTS fallback against the AOSP `android-4.3.1_r1` tag, and uses the same AOSP tag for the old CM SVOX entry. ## Attach APN and RIL comparison

The pre-reboot G900T radio log is preserved at `diagnostics/kltetmo/network-scan-2026-11-26/`. It shows the modem scanning AT&T (`310410`, CURRENT), Verizon (`311480`, AVAILABLE), and T-Mobile (`310260`, AVAILABLE). Manual selection of `310410` is acknowledged by QMI, but the resulting framework state remains out of service. Repeatedly, Samsung RIL reports preferred APN database row `1508`, then `db prepare error` and `Failed to load attach apn`.

The CM10.2 D801 comparison (`android_device_lge_d801`, branch `cm-10.2`, commit `c020cf9eee95409c242aefba9522423c5db5f9b4`) uses Qualcomm's `libril-qc-qmi-1.so` stack from its donor firmware. Jelly Bean `DcTracker.createAllApnList()` obtains APNs through `TelephonyProvider`, filtering by SIM operator numeric and `carrier_enabled`, then selects a preferred APN. CM10.2 telephony has no `RIL_REQUEST_SET_INITIAL_ATTACH_APN` or `setInitialAttachApn()` API. This is useful for the JB framework's normal data-call path, but it does not explain Samsung's private database lookup.

The S5 CM11 source (`android_device_samsung_klte`, branch `cm-11.0`, commit `c5a0e62e32081e7029e32e244ce1ccf30e4f37a8`) pairs Samsung's `rild`, `libril.so`, and `libsec-ril.so` with `KlteRIL`. CM11's telephony commit `4bb8fc3e471a8a3c1aeba9682c1448b50c46a15d` adds `DcTrackerBase.setInitialAttachApn()` and `RIL_REQUEST_SET_INITIAL_ATTACH_APN`; the CM10.2 telephony commit `913bd2582073ec077c2282a2ec10f74b99aa40d7` has neither. The captured Samsung radio log contains `invalid command block ... RIL_REQUEST_SET_INITIAL_ATTACH_APN`, demonstrating that this Samsung RIL rejects standard request 111. This request rejection is distinct from the later, independently identified SQL schema failure.

The query is now identified from the target G900T `libsec-ril.so`. Its `DataCallManager::LoadApnProfile()` prepares variants of `SELECT _id,apn,type,protocol,user,password,authtype,carrier_enabled,max_conn,max_conn_t,wait_time FROM carriers ...`. CM10.2 `TelephonyProvider` defines the first eight selected columns but not `max_conn`, `max_conn_t`, or `wait_time`. A read-only copy of the live database confirms APN row 1508 exists; replaying the vendor query fails with SQLite `no such column: max_conn`. Thus the error is a real Jelly Bean-provider/Samsung-RIL schema mismatch, not a missing APN row. The CM11 provider snapshot (`ab985cdbc7ed847feecd0bdbb8d81b2249c7da6a`) also lacks those Samsung-specific columns, so this incompatibility is not fixed by importing the full CM11 provider.

The provider now adds these three integer columns with default zero and migrates existing databases to schema version 10. Zero represents no RIL-side connection cap or extra retry wait. The full database copy used to inspect the schema was removed after recording the relevant query and result in `diagnostics/kltetmo/network-scan-2026-11-26/README.md`.

CM11's standard `setInitialAttachApn()` serializes request 111 through Java `RIL` and generic `libril` (`android_hardware_ril` commit `6c5c9563a58da6e0dac554da4a26613b31cb4a1f`). However, the saved S5 radio log records Samsung's proprietary request router rejecting `RIL_REQUEST_SET_INITIAL_ATTACH_APN` as an invalid command block. The S5 blob already implements its own `RefreshAttachApn` / `IsAttachApnChanged` path and reads APN profiles from `TelephonyProvider`; do not send request 111 to this vendor RIL unless a Samsung-specific adapter is identified. First rebuild/install the provider schema migration and confirm the vendor's database query succeeds; then assess whether framework attach-APN API work is still needed. The captured out-of-service state remains a separate registration issue; successful APN lookup alone will not prove LTE registration or packet data.

## Interface decisions

- **Boot and storage.** Keep S5's board DTS, kernel, 2 KiB boot pages, DT table, partition labels and CM11 boot offsets. The G2 also uses separated DT packaging, with different ramdisk and tags addresses. Use S5's target ramdisk data and adapt the CM11 `sdcard` command line and USB/microSD fstab records to the Jelly Bean daemon and vold syntax. Jelly Bean init understands `mount_all`. CM11 added `restorecon_recursive`. Port and audit the target file labels before device use.
- **Graphics.** G2 and Togari have open Jelly Bean MDSS HWC/gralloc and V4L2 media sources. Use both at the OS revision. Compare `msm_mdp.h`, ION heap IDs, buffer layout and fences against the S5 kernel before accepting frame, compositing or codecs as working. The S5 uses the MSM8974AC board DTS and Adreno 330. It changes `MSMFB_NOTIFY_UPDATE` from write-only to read/write and adds fields to MDP structs. Its ION header moves the system heap from 30 to 25, moves the camera heap from 20 to 30, and aliases the IOMMU heap to the system heap. Its KGSL header adds the submit-commands API. Build the open display and V4L2 sources with exported S5 kernel headers. These differences keep the S5 EGL and G2 EGL candidates distinct. [G2 release kernel](https://github.com/CyanogenMod/android_kernel_lge_msm8974/tree/72494f762a876ed1831329263bf18bcbe965ebf6/include/linux) [Sony M1 kernel](https://github.com/CyanogenMod/android_kernel_sony_msm8974/tree/dac7bc649f9fd0436e00112c5221409998d94a50/include/linux)
- **Audio.** Start with G2's JB CAF HAL and the S5's mixer and routing tables. The S5 DTS exposes `msm8974-taiko-mtp-snd-card`, recognized by the JB ALSA HAL. The HAL opens a `snd_soc_msm_Taiko` use-case table, so the S5 CM11 mixer XML needs translation to JB routes. Validate ACDB IDs, offload capabilities and audience firmware on the target before enabling the corresponding paths.
- **GPS.** The source-built Qualcomm HAL and `libloc_api_50001` implementation are taken from the verified S5 common CM11 tree at `b9518a421546758aa3bea094e22845b6424cc62f`, not a donor handset. The HAL is named `gps.msm8974`; Android 4.3's hardware loader falls through from `ro.hardware=qcom` to `ro.board.platform=msm8974`, selecting it. CM11's `ContextBase` dynamically loads `liblbs_core.so` as the LBS proxy; that proxy constructs the concrete `LocApiV02` backend using `libloc_api_v02.so`. The NCH versions of both, plus `libizat_core.so`, match the hashes in the CM11 S5 vendor archive. Without the LBS/Izat libraries, the HAL selects its no-op `LocApiBase` fallback. Android 4.3 lacks several later GNSS delete-flag names used only in CM11 logging; those log-table entries were removed to compile the API 18 port. The KitKat geofence extension is excluded because its new context ABI crashes Jelly Bean `system_server`; the API 19 Qualcomm location APK/FLP path is also outside this initial fix test.
- **Radio.** Preserve API 18's `Phone`, TelephonyProvider, Stk and APN/SPN configuration. Verified CM11 klte source selects `KlteRIL` through `BOARD_RIL_CLASS` and `ro.telephony.ril_class`, and packages matching Samsung `bin/rild`, `lib/libril.so` and `lib/libsec-ril.so`. Its Java adapter consumes five retry-count integers after each SIM application's standard fields. CM10.2 already contains `SamsungQualcommRIL`, whose card-status parser consumes the same five integers. The 440-byte G900T callback matches a 24-byte header plus eight 52-byte records by size, although the raw layout still needs direct confirmation. A live overlay with the complete NCH native RIL trio and `SamsungQualcommRIL` produced `CARDSTATE_PRESENT`/`APPSTATE_READY`, kept `rild` alive past the prior crash interval, and left `gsm.sim.state=READY`. The installed T-Mobile OTA builds the CM11 target-device `KlteRIL` into API 18 `telephony-common` and selects it through `BOARD_RIL_CLASS` and `ro.telephony.ril_class`. The post-flash baseband regression was traced to modem firmware being absent from the kernel's `/firmware/image` lookup path: a temporary merged view from `/firmware` and `/firmware-modem` loaded MBA/modem, restored baseband `G900TUVU1ANCH`, and returned SIM state `READY`; operator/registration/signal queries now complete. The preserved mode 12 was changed to mode 9; data registration reports 12 (searching, emergency calls only), voice reports 2 (searching), and signal values remain invalid. The mapping needs a persistent boot-time fix; LTE registration/data still need validation. The Samsung Galaxy Note 3 LTE is a same-vendor MSM8974/Adreno 330 comparison, but Git refs verified here expose CM11 device/common trees only; its kernel has a CM10.2 branch. Its `HlteRIL` uses the same five SIM retry-counter reads as `KlteRIL` and adds a custom data-registration parser that normalizes RAT `102` to `2`. That code path translates RAT 102 to EDGE. There is no evidence this handset reports 102; current CM11-derived RIL responses show searching/emergency-only and invalid signal, so do not apply that EDGE translation as an LTE fix. The Note 3 source is CM11-only and its private radio libraries are not candidates for reuse; treat it as a protocol and initialization comparator, not a confirmed public CM10.2 radio port. [CM11 klte adapter](https://github.com/CyanogenMod/android_device_samsung_klte/blob/c5a0e62e32081e7029e32e244ce1ccf30e4f37a8/ril/telephony/java/com/android/internal/telephony/KlteRIL.java) [CM11 klte RIL configuration](https://github.com/CyanogenMod/android_device_samsung_klte/blob/c5a0e62e32081e7029e32e244ce1ccf30e4f37a8/BoardConfig.mk) [CM11 RIL blob inventory](https://github.com/CyanogenMod/android_device_samsung_klte/blob/c5a0e62e32081e7029e32e244ce1ccf30e4f37a8/proprietary-files.txt) [CM11 Note 3 RIL adapter](https://github.com/CyanogenMod/android_device_samsung_hlte/blob/e144e6028638a5a021c91246a9aa731202ea43ac/ril/telephony/java/com/android/internal/telephony/HlteRIL.java) [CM11 native serializer](https://github.com/CyanogenMod/android_hardware_ril/blob/6c5c9563a58da6e0dac554da4a26613b31cb4a1f/libril/ril.cpp)
- **Camera, sensors, GPS, charging and power.** Use Samsung CM11 target configuration and target-owned firmware. Camera HAL and stagefright interfaces need separate comparison against JB.
