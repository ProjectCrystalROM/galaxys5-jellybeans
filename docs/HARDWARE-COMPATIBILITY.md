# Hardware compatibility

The SM-G900T now reaches `sys.boot_completed=1` and Setup Wizard. This is an early boot milestone, not a declaration that the hardware is functional. “Configured” means a source configuration or integration entry exists. “Pending” means a required implementation or compatibility check is still open.

| Subsystem | Checkout status | Physical evidence still needed |
| --- | --- | --- |
| Kernel and board DT | Both S5 kernels and QCDT images compiled | Bootloader accepts image, kernel initializes board |
| Recovery | Original image booted in preliminary device testing. Updated font and keys verified at build level | Check readability and physical button handling |
| Init, partitions, ADB | G900T reaches completed Android boot. USB debugging had to be enabled manually; the host then authenticated. Root access was subsequently enabled and `adb root` now returns uid 0. | Verify ADB behavior on cold boot |
| Launcher and Settings | G900T reaches Setup Wizard; initial services and UI are available | Confirm sustained UI stability and usable Settings |
| Display/touch/buttons | Display reaches Setup Wizard. Charge LED and capacitive-button lighting, including timeout, physically work | Touchscreen, physical buttons, and full UI interaction |
| Accelerated graphics and media | JB MDSS/V4L2 candidates selected | ION/HWC/codec ABI, rendering and hardware decode |
| Internal, microSD, USB, MTP | USB ADB works after manually enabling USB debugging and authorizing the host | Internal and microSD access, cold-boot USB behavior, MTP transfer |
| Wi-Fi | S5 `bcmdhd4354` registers `wlan0`; STA/AP firmware and NVRAM are present. Correct S5 sysfs firmware path made netd reload succeed, and the init socket lookup made supplicant initialize. A temporary bind mount matching CM10.2's expected control-socket directory allowed scans, 5 GHz WPA2 association, DHCP, and a successful Google page load. OTA `574dc9f24d` includes the boot-time socket-path link; persistence after factory reset has not been isolated from other live-overlay testing. | Confirm scan, association, DHCP and internet access across cold boot and factory reset; check firmware/NVRAM and MAC persistence |
| Bluetooth | G900T discovery and pairing are physically confirmed. PAN reports connected without passing packets; PdaNet+ DUN did not connect. A2DP reaches connected/playing state and AudioPolicy routes music to the paired sink, but the sink is silent. AudioFlinger shows the A2DP output thread blocked in HAL `write` with zero successful writes. The captured log ends at `start_audio_datapath`; source inspection shows the next operation sends A2DP START on the control socket and waits synchronously for Bluedroid's acknowledgement. There is no subsequent `.a2dp_data` socket connection log, so the present evidence points to the START control handshake/media-task path, before PCM reaches the data socket. PAN's BNEP data path is separate from A2DP's AVDTP/media path, though both depend on the shared Bluetooth stack/controller. The target kernel config disables `CONFIG_BT_BNEP`, `CONFIG_BT_RFCOMM`, and `CONFIG_PPP_ASYNC`, likely explaining PAN/DUN data failures. A patch enabling those protocols is compiled into the combined test OTA, not yet installed. | Trace why Bluedroid does not complete the A2DP START control handshake; separately install the protocol-enabled kernel and retest PAN/DUN with packet counters. Then test A2DP audio, file transfer, and suspend/resume. |
| Audio | ADSP, Slimbus, Taiko, and the S5 sound card register. The card appears around 8.3 seconds. Source inspection identified why timer increases did not fix cold-boot audio: `ALSADevice` opened `/dev/snd/controlC0` before card detection, retaining an invalid mixer handle. The readiness-gated HAL waits for card registration before constructing `ALSADevice`. Corrected UCM uses the S5's `DAC1 Switch` and 0–8 speaker-driver range. WAV playback has been physically heard through raw PCM, Stagefright/AudioTrack, and the built-in player. Default notification audio was confirmed again after a factory reset, though its volume is low at maximum setting. ACDB loader dlopen still fails; capture, headset and recording paths remain unvalidated. | Validate notification volume behavior; physically test headset, microphone, recording and internet voice |
| GPS | Stock `G900TUVU1ANCH` (Android 4.4.2) physically acquired a fix with 21 satellites reported by GPS Toolbox; stock logcat shows GNSS SV-info indications and TTFF 15.82 s. Stock `/system/etc/gps.conf` matches the current target config and also leaves `SUPL_HOST` unset. On the CM10.2 `a66f4ac09d` OTA, the HAL forwarded GNSS SV info to Android (up to 21 in view); GPS Toolbox showed fewer satellites and 0 used, but a fresh GPS-provider location arrived at 3 m with favorable DOP. That fix was obtained offline with the system date set to 2013. After a full power-off/on, the user reports the earlier no-fix behavior returned even after automatic network time restored the clock. Retained GNSS aiding/state from the preceding stock session is suspected but not isolated. The follow-up ADB snapshot had Settings in the foreground, so it does not establish whether the cold session receives SV callbacks. Some QMI reports return `LOC_SESS_FAILURE`; reliable cold-start operation is not validated. | With GPS Toolbox actively requesting location, capture a cold-start log through SV acquisition, QMI session state, and a fresh fix. Compare behavior before and after internet assistance; avoid wiping modem data until a recovery plan is agreed. Keep stock logs local because they contain location data. |
| Sensors, camera | Candidate inventories available, integration pending | Sensor event delivery, photo/video capture |
| Charge, thermal, power | S5 kernel protections and target thermal configuration included | Charging/temperature readings, daemon compatibility, charge limits, suspend and power behavior |
| G900T radio/SIM | With the NCH RIL binaries and target-hardware `KlteRIL`, the modem reports baseband `G900TUVU1ANCH`, SIM is readable, and manual network selection registers on AT&T LTE (`310410`). Incoming carrier billing SMS messages were received. The modem firmware search-path overlay was used during earlier bring-up; current clean-boot persistence of that path should be verified separately. | Verify radio registration, SMS, and reconnect persist after clean install and cold boot; test airplane mode |
| G900T APN/data | The Samsung RIL's APN query requires `max_conn`, `max_conn_t`, and `wait_time`; TelephonyProvider schema v10 adds these fields. A further v11 migration and null-safe `DcTracker` fix address NULL MVNO metadata in the AT&T `nxtgenphone` row, which had crashed `com.android.phone`. After factory reset, the phone process remained available and packet data reached the AT&T captive billing portal after manually selecting the APN. Automatic APN preselection was absent; with multiple AT&T SIM/APN profiles, this is recorded as a SIM/profile-dependent provisioning limitation rather than a proven radio defect. | Record the exact SIM/plan and selected APN for repeatability; test data reconnect after reboot and with other SIM profiles if available |
| G900T incoming SMS | BasicSmsReceiver is packaged with classes.dex and SDK 18. Incoming carrier billing SMS messages were physically received during radio testing. Voice is disabled and SMS remains enabled in compiled resources. | Confirm BasicSmsReceiver delivery and multipart SMS after clean install |
| G900V CDMA/EVDO/LTE | Variant properties present, RIL ABI pending | CrystalBTS registration, voice, SMS, EVDO and separate LTE test |
| Fingerprint, heart rate, Samsung apps | Outside initial scope | — |

When an approved image is available, first establish kernel → init → mounts → ADB → native services → SurfaceFlinger → Zygote → System Server → boot animation → launcher and Settings. Capture failures at each boundary. Follow with charging and thermal checks before sustained graphics or radio tests.
